# ImageAll 智能标签照片推流规格

> 状态：Accepted（V1 已实施）
>
> 日期：2026-09-02
>
> 相关：`ADR-067-CONTEXTUAL-TAG-FEED.md`、`STAGE-3-REVIEW-QUEUE-IMPLEMENTATION-SPEC.md`、
> `TRAINING-WORKSPACE-SPEC.md`、`LOCAL-TEST-DATA-SAFETY.md`

## 1. 问题

ImageAll 的个人模型依赖用户先提供正、负标签样本；用户标签较少时，模型还不能稳定产出候选，用户却需要
逐张寻找并标记同一事件中的照片。媒体本身通常带有拍摄时间、GPS、设备信息，文件夹来源还可能保留相机、
手机或导出工具生成的文件名序列；当用户确认其中一张照片属于某标签时，时间接近、空间接近、设备一致或
文件名连续的一组媒体很可能属于同一拍摄事件。

这些上下文都只能作为候选证据，不能直接成为标签事实。产品需要把多路证据形成的候选组以可解释的照片
推流呈现给用户，让用户批量确认、排除个别照片或忽略整组，并把明确决定继续交给现有标签与训练链路。

## 2. 目标

1. 在个人模型尚未达到训练门槛时，也能从已有人工标签产生可审核候选。
2. 把连续照片的一次标签操作，从逐张处理缩短为一次组审核和必要的少量排除。
3. 每条候选都显示拍摄时间差、空间距离、设备一致性、来源目录或文件名序列等可解释证据；不把启发式分数
   冒充概率。
4. 用户确认或明确拒绝后，继续写入现有 `asset_tag_decision`，成为当前模型训练可用的人工事实。
5. 为后续叠加设备元数据完善、DINOv2、个人模型和更细粒度标签保留多证据扩展点，不在首版耦合模型推理。

### 2.1 首版成功指标

- 数据安全：自动推流写入原图或受保护来源的次数必须为 `0`；自动写入人工标签决定的次数必须为 `0`。
- 可解释性：`100%` 候选组可展示锚点照片和至少一条具体上下文证据；缺失 GPS、时间或设备时明确降级，
  不伪造“同一事件”依据。
- 操作闭环：确认、明确拒绝、忽略、稍后处理四种结果均可持久化并在重启后保持。
- 质量假设：试用期内，至少 `70%` 被处理的候选组包含 `2` 张及以上被用户确认的新照片；正式目标在取得
  首轮基线后再校准。
- 效率假设：对最终确认 `5` 张及以上的组，从首次打开到提交的中位交互次数不超过 `3` 次。

## 3. 非目标

- 首版不根据任何上下文证据自动给照片打标签；所有标签事实仍由用户动作产生。
- 首版不把 Apple Photos 的原始文件名当作“同目录”证据；Photos 资产可使用已经入库的时间与位置，但
  PhotoKit 不提供与文件夹来源等价的稳定目录语义。
- 首版不执行图片解码、embedding 或模型推理；规则推流必须能在纯目录元数据上独立运行。
- 首版不构建跨来源、跨目录的事件识别，也不承诺文件名邻近一定代表同一事件。
- 首版不把“忽略该组”写成负样本；明确负标签必须由单独且清晰的用户动作产生。
- 首版不为补齐设备信息自动重读全库原始媒体；设备采集与历史回填必须作为有界、可取消且明确授权的独立
  增强步骤。

## 4. 用户故事

1. 作为正在整理旅行照片的用户，我确认一张照片属于“旅游”后，希望看到同目录、文件名连续的候选组，
   从而一次确认同一事件的多张照片。
2. 作为重视标签质量的用户，我希望在提交前取消选择组内少数无关照片，避免整组误标。
3. 作为不认可这组上下文证据的用户，我希望忽略整组而不制造模型负样本。
4. 作为确信某些照片不属于该标签的用户，我希望显式把选中照片标为“不属于”，让它们成为真实负样本。
5. 作为已经拥有个人模型的用户，我希望以后在同一候选卡上看到“文件序列”和“个人模型”分别提供的证据，
   但最终仍只做一次标签决定。
6. 作为使用多个相机或手机拍摄的用户，我希望系统把设备一致性作为辅助证据，但不能因为“同一台手机”就
   把跨越数月的照片判为同一事件。

## 5. 首版用户流程

```text
用户确认“IMG_1042.JPG 属于旅游”
                    │
                    ▼
上下文事件生成器（首版只读已入库元数据）
时间邻近 + 空间邻近 + 文件序列 + 来源上下文；缺失信号可退化
                    │
                    ▼
持久候选组：锚点 1 张 + 待确认候选最多 23 张
                    │
                    ▼
智能推流：预览、证据说明、默认选中候选、允许逐张排除
        ┌───────────┼────────────┬────────────┐
        ▼           ▼            ▼            ▼
  确认选中照片   明确标为不属于   忽略该组      稍后处理
        │           │            │            │
 accepted 决定   rejected 决定   仅组状态      保持 pending
        └───────────┴────────────┴────────────┘
                    │
                    ▼
      现有 Review / 训练样本 / 撤销链路
```

### 5.1 入口与呈现

- Mac 首版在“待审核建议”附近增加“智能推流”入口和待处理组数。
- 进入入口时最多检查最近 `200` 条已接受标签的已入库元数据；新确认标签会即时尝试生成。该过程不重读
  原始媒体，也不申请新的来源权限。
- 一次展示一组；顶部固定显示标签、锚点照片与证据摘要，例如“相隔 8 分钟、约 320 米、文件名连续”；
  主体使用现有照片网格和预览能力。
- 候选默认选中，并提供完整桌面选择模型：普通单击单选、`⌘` 单击增减、`Shift` 单击连续范围、普通拖框
  多选、`⌘A` 全选和 `⇧⌘A` 清除选择；同时提供可点击的“全选 / 清除选择”控件。
- 已确认锚点只展示，不能被选择、取消或重复提交；框选和全选结果在进入业务模型时必须再次过滤为候选成员。
- “忽略该组”与“将选中的 N 张标为不属于「标签名」”都是底部直接可见动作；明确负标签不得收进“更多”
  菜单。接受与拒绝按钮都必须显示将处理的选中数量和标签名。
- 提交后选择下一组，不重载整个已浏览窗口，不把视口跳回第一页。

## 6. 多信号候选规则

### 6.0 当前元数据能力与缺口

| 信号 | 当前目录库能力 | 首版处理 |
|---|---|---|
| 文件名 / 来源内目录 | 文件夹资产已有 `file_name`、`relative_path`、`source_id` | 直接使用 |
| 拍摄时间 | `asset.media_created_at_ms`；文件夹图片只在 EXIF 含明确时区时可靠写入，Photos 使用 PhotoKit 时间 | 直接使用；不拿文件修改时间冒充拍摄时间 |
| GPS / 地点 | `asset_location` 已保存图片 embedded GPS、Photos GPS 或明确地点标签 | 直接使用；保持来源优先级 |
| 媒体类型 / 尺寸 / 时长 | 图片和视频已有类型、尺寸，视频可有时长 | 只作解释与边界，不单独决定事件 |
| 拍摄设备 | 当前没有持久化相机厂商、型号或镜头；文件夹视频的拍摄时间/GPS 也存在缺口 | 作为 V1.1 元数据增强，首版不得伪造 |

### 6.1 资格

候选资产必须同时满足：

- `locator_state = current`、`availability = available`，且没有处于回收生命周期；
- 与锚点属于同一 `source_id`；文件夹与 Photos 来源都可分别参与，跨图片/视频允许进入同一事件组，但 UI
  必须正确预览各自媒体类型；
- 目标标签不存在已确认或已拒绝的 `asset_tag_decision`；
- 生成器只查询已经入库的元数据，不解析绝对路径、不申请来源访问权限，也不为生成推流重新读取原始媒体。

### 6.2 证据类型

- `captureTime`：比较可靠的 `media_created_at_ms`。文件修改时间只能显示为文件事实，不进入首版事件打分。
- `spatialProximity`：根据 canonical `asset_location` 计算距离；GPS、Photos GPS 和地点补全的来源必须保留。
- `filenameSequence`：仅用于文件夹资产；同父目录、同命名骨架且序号连续。
- `sourceContext`：同一来源或同一来源内目录是辅助证据，单独不足以建立事件组。
- `captureDevice`：同一设备只能增强时间/空间/文件序列证据，永远不能单独建立事件组；当前字段缺失，V1.1
  才启用。
- `visualModel` / `personalModel`：V2 才加入，原始分数与上下文证据分开呈现。

### 6.3 首版成组策略

候选先按锚点建立有界邻域，再以可解释规则连边。满足以下任一条件才可进入同一候选组：

1. 同父目录、同命名骨架，且相邻序号差不大于 `3`；
2. 拍摄时间相差不大于 `30` 分钟，且空间距离不大于 `5` 公里；
3. 拍摄时间相差不大于 `10` 分钟，且来自同一文件夹来源；
4. 同一自然日、空间距离不大于 `500` 米，并且至少还有文件序列或来源上下文之一支持。

`context-event-v1` 为了跨设备稳定复现，以 UTC 日历日判定“同一自然日”；后续若 catalog 持久化可靠的
拍摄时区，再通过新策略 revision 引入拍摄地自然日，不能静默改变现有组身份。

目录、地点或设备一致性单独都不能成组。首版阈值属于 `context-event-v1` 策略，可在合成与人工试用基线后
升级；UI 必须展示实际命中的规则，而不是一个不可解释的总概率。

对于“旅游”这类跨多日、跨地点的宽标签，首版只推送锚点附近的高置信局部事件，不因一次确认自动扩成整个
旅行。用户确认新成员后，可以从新的锚点继续产生下一组。

### 6.4 命名骨架与连续段

- 去掉扩展名，对 Unicode 做稳定大小写折叠，将连续数字段替换为 `#`，分隔符归一化，得到命名骨架；
  例如 `IMG_01042.JPG` 和 `img-01043.heic` 可归入同一候选骨架。
- 首版以最后一个数字段作为序号；数字宽度不同、无数字段或骨架不兼容时不自动跨组。
- 从锚点向前后扩展；相邻序号差大于 `3`、遇到该标签的明确拒绝、目录变化或骨架变化时停止文件序列扩展；
  其他时间/空间路径仍需独立满足成组规则。
- 每组最多 `24` 张（含锚点）；超过上限时按离锚点的序号距离截断，并在 UI 标明还有相邻媒体未纳入。
- 同一标签、来源和策略版本内若新的候选集合与 pending 组重叠，保留并复用最早的 pending 组，避免多个锚点
  生成重复推流；若组内候选已在其他入口获得人工决定，旧组自动结束，再从近期 accepted 锚点生成剩余候选。

### 6.5 缺失值退化

- 没有 GPS：可由短时间邻近加文件序列/来源上下文成组；不得推算坐标。
- 没有可靠拍摄时间：可由文件序列成组；不得用复制后的修改时间替代拍摄时间。
- 没有文件名目录语义（Photos）：可由时间加空间成组。
- 没有设备：其余证据照常工作；UI 不显示“设备相同”。
- 只有一个弱信号：不生成组，宁可漏召回，不用低质量候选污染人工工作流。

### 6.6 冲突与优先级

1. 人工 `asset_tag_decision` 永远优先，已决定资产不再作为待确认候选。
2. “忽略组”只抑制同一策略版本和同一组身份；标签事实变化或策略升级后可生成新组。
3. 同一资产与标签若同时有模型建议，首版保持现有模型 Review 行不变；智能推流独立呈现。
4. 后续证据融合只合并展示，不把不同模型的原始 score 直接相加，也不隐藏各自来源。

## 7. 数据与应用契约

已新增 migration `v038_add_contextual_tag_feed`，物理表名如下：

### 7.1 `contextual_tag_feed`

| 字段 | 含义 |
|---|---|
| `id` | UUID 主键 |
| `tag_id` / `anchor_asset_id` / `source_id` | 标签、锚点与来源外键 |
| `group_key` | 标签、来源、排序无关的成员集合与策略形成的稳定摘要；不存敏感绝对路径 |
| `policy_revision` | 首版固定为 `context-event-v1` |
| `state` | `pending`、`dismissed`、`resolved` |
| `revision` | 乐观并发版本；提交时必须匹配 |
| 时间列 | 创建、更新、处理时间 |

唯一约束：`tag_id + source_id + group_key + policy_revision`。`group_key` 已包含排序无关的成员集合、标签、来源
与策略 revision，因此同一成员组不会因锚点不同重复出现。

### 7.2 `contextual_tag_feed_member`

| 字段 | 含义 |
|---|---|
| `feed_id` / `asset_id` | 联合主键与外键 |
| `role` | `anchor` 或 `candidate` |
| `rank` | 组内稳定排序，不等于模型分数 |
| `evidence_mask` | 成员命中的证据类型集合 |

### 7.3 `contextual_tag_feed_evidence`

| 字段 | 含义 |
|---|---|
| `feed_id` / `asset_id` / `kind` | 成员的一条上下文证据；kind 为时间、空间、文件序列、来源或设备 |
| `strength` | 本策略内部的排序强度，不是标签概率 |
| `delta_ms` / `distance_m` / `sequence_offset` | 可选的可解释差值 |
| `provenance` | `embeddedGPS`、`photosGPS`、`placeTag` 等来源；不复制绝对路径或原始坐标 |

设备增强建议另建 `asset_capture_device`，至少持久化规范化厂商、型号、来源与 revision。历史回填必须是显式、
有界、可暂停的 metadata job；不能因为打开智能推流而自动遍历原始媒体。

生成、刷新、确认和状态更新都在数据库事务中完成。确认请求携带 `feed_id + revision + selected_asset_ids`；
若成员或版本已变化，返回 `feedChanged` 并刷新，禁止在陈旧组上静默提交。

### 7.4 决策复用

- “确认选中照片”调用现有 `batchAccept`；“明确标为不属于”调用现有 `batchReject`。
- 现有批量决定负责快照和撤销；推流不得另建第二套标签事实。
- 决策成功与 feed `resolved` 必须在同一数据库事务，避免标签已写入但组仍显示 pending。
- 仅忽略时只更新 feed 状态，不触碰 `asset_tag_decision`、模型产物或原始媒体。

## 8. 分期

### V1：Mac 最小纵向闭环

- `context-event-v1` 使用已入库的文件名、目录、拍摄时间和位置生成候选；
- v038 持久组、成员、多路证据、幂等刷新与并发校验；
- “智能推流”入口、单组网格、桌面多选/全选、确认、直接可见的明确拒绝、忽略、稍后处理；
- 一个主路径、一个“忽略不产生负样本”失败保护、现有批量标签回归；
- 仅用临时数据库和合成文件名、时间、坐标验证，不读取受保护真实照片。

### V1.1：设备与视频元数据增强

- 文件夹图片新增 EXIF make/model/lens 的安全提取与 `asset_capture_device`；
- 补齐可验证的 QuickTime/AVFoundation 拍摄时间、GPS 和设备字段，不能解析时保持 NULL；
- 新资产随 reconcile 写入；历史资产仅通过用户明确启动的有界 job 回填；
- 设备一致只能增强其他证据，不能单独生成事件组。

### V1.2：Web Companion 对等

- Remote DTO / API、Web 路由与相同四动作；
- Host 继续作为组和标签决定的权威来源；
- 保持浏览窗口、选择与滚动连续性。

### V2：模型证据与细粒度标签

- 在上下文候选组内按 DINOv2 / 个人模型结果显示独立证据徽章；
- 允许从“旅游”候选组继续询问“海滩”“雪山”“博物馆”等更细粒度标签；
- 基于已处理组的结果学习阈值或排序，但不得把“忽略”当负例；
- 评估事件时间、地理位置、设备 burst 等新证据，仍保留来源解释。

## 9. 验收

1. 合成目录 `IMG_01040` 至 `IMG_01047` 中，确认 `IMG_01043` 后由文件序列生成稳定、幂等的候选组。
2. 无目录语义的合成 Photos 资产可由“30 分钟内 + 5 公里内”生成候选，缺失 GPS 时不会伪造位置证据。
3. 同目录但跨数月、同设备但无其他证据、同地点但跨日期的资产不会仅凭单一弱信号误入组。
4. 对组内一张照片已有明确拒绝时，生成器不覆盖拒绝事实，也不通过该节点扩散标签。
5. 确认选中的 N 张只写 N 条 accepted；取消选择的照片保持 unknown。
6. “忽略该组”后 `asset_tag_decision` 行数不变；显式“不属于”才写 rejected。
7. 陈旧 revision 的提交失败并刷新，不产生部分标签决定。
8. 重启后 pending / dismissed / resolved 状态保持；同一触发重复运行不产生重复组。
9. 普通单击、`⌘` 单击、`Shift` 连选、拖框、`⌘A`、`⇧⌘A` 和可见“全选 / 清除选择”控件产生一致
   的候选选择；锚点不能进入 accepted / rejected 提交。
10. 明确“不属于”动作始终直接显示在底部操作区，不依赖“更多”菜单。
11. Debug 构建、相关测试、数据库 `quick_check`、外键检查和 `git diff --check` 通过。
12. 自动化测试不访问 `/Volumes/HDD2/Photos Library.photoslibrary` 或 HDD2 顶层年份目录。

## 10. 已确认的首版产品选择

项目所有者于 2026-09-02 以“开始实施”批准推荐方案：

1. Mac 首版采用侧栏“智能推流”独立入口。
