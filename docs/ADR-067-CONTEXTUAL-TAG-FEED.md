# ADR-067：智能标签推流采用可解释的多信号上下文候选组

> 状态：Accepted
>
> 日期：2026-09-02
>
> 相关：`SMART-TAG-FEED-SPEC.md`、ADR-054、ADR-061、`TRAINING-WORKSPACE-SPEC.md`

## 背景

ImageAll 的 Feature Print、个人质心和 AdamW 建议都需要人工标签样本。样本不足时，用户仍能从拍摄时间、
GPS/地点、设备以及文件夹来源的目录和文件名序列发现同一事件的一批照片。若把这些启发式直接塞进某个
模型 prediction 表，来源会变得不可解释，忽略行为也可能被误写成训练负样本；若每次临时计算而不持久化，
又无法支持去重、稍后处理、重启恢复和多端一致性。

## 决策

### CT-P1：上下文推流由多路独立证据组成，不是模型预测

- 首版 evidence kind 包括 `captureTime`、`spatialProximity`、`filenameSequence` 和 `sourceContext`，策略身份为
  `context-event-v1`；`captureDevice` 在元数据契约补齐后加入。
- 首版只读取 catalog 中已经存在的拍摄时间、canonical location、来源、相对路径、文件名和人工决定；不重新
  读取媒体、不申请来源书签访问、不启动 Core ML。
- 每路证据保留差值和 provenance。UI 不把内部强度显示为标签概率，也不把模型 score 与上下文强度直接相加。
- 同目录、同地点或同设备单独都不足以成组；设备一致性只能增强时间、空间或文件序列证据。

### CT-P2：候选以持久组呈现，标签事实仍走既有决定表

- 新增 `contextual_tag_feed`、`contextual_tag_feed_member` 与 `contextual_tag_feed_evidence`，持久保存
  pending / dismissed / resolved、组成员、独立证据、策略版本和乐观并发 revision。
- 接受与明确拒绝复用 `asset_tag_decision` 的批量事务和撤销语义，不复制人工事实。
- “忽略组”只更新候选组 disposition，绝不生成 rejected 决定。

### CT-P3：先复用现有元数据形成闭环，再独立补齐设备和视频元数据

- V1 复用现有文件名、目录、拍摄时间和位置，交付“确认一张照片 → 生成组 → 浏览预览 → 排除个别 →
  批量确认/忽略 → 训练样本可见”的 Mac 闭环。
- Mac 入口在打开时有界检查最近 `200` 条 accepted 决定；新接受决定即时触发生成。两条路径都只读 catalog
  元数据，不扫描或重读原始媒体。
- 当前 catalog 没有拍摄设备字段，文件夹视频也未完整写入拍摄时间/GPS；V1 不得把缺失字段假装为已知。
- V1.1 新增 `asset_capture_device` 和有界 metadata backfill；打开推流不能隐式触发全库原始媒体遍历。
- Web Companion 在 V1.2 通过 Remote DTO/API 读取与处理同一持久组，不在浏览器重算上下文规则。
- 自动化只使用临时数据库、合成路径与合成预览；受保护真实照片不进入测试。

### CT-P4：模型增强合并证据展示，不合并人工决定身份

- 后续 DINOv2、个人模型或标准模型可为 feed member 附加独立 evidence badge。
- 同一 `asset_id + tag_id` 在推流中只需一次人工决定；UI 必须保留每个证据来源与原始分数语义。
- 现有 Review Queue 的多 origin 比较契约保持不变；首版智能推流不改写其排序和分页。

### CT-P5：Mac 推流使用完整桌面选择模型，明确负标签直接可见

- 候选组复用图库的桌面选择语义：普通单击替换选择、`⌘` 单击增减、`Shift` 单击连续范围、普通拖框多选，
  `⌘A` 全选、`⇧⌘A` 清除选择；界面同时提供可点击的全选与清除控件。
- 键盘快捷键通过窗口内 AppKit event monitor 处理，跨网格焦点保持生效；文本框、搜索框正在编辑时不得拦截。
- 高频决定与 Review Queue 对齐：`P` 确认属于、`X` 确认不属于、`U` 稍后处理；智能推流额外以 `I`
  忽略整组。决定键允许无修饰键或 `Shift` 大写输入，拒绝 `Command`、`Control`、`Option` 组合，避免覆盖系统操作。
- 最近一次确认或拒绝可通过底部“撤销上一步”或 `⌘Z` 恢复。撤销在同一数据库事务内恢复所选照片原标签
  状态并重新打开候选组；若照片决定或候选组已经被后续操作改变，则拒绝覆盖较新的事实。
- 锚点与候选成员都可进入照片标签编辑选择；底部 `P` / `X` 的提交集合仍必须与 candidate 成员求交集，
  anchor 永远不会被当作候选重复提交。
- 右侧检查器复用图库标签 chip：左键确认标签、右键清除决定、支持批量混合状态和创建新标签。若用户清除
  anchor 对当前 feed 标签的接受决定，保留当前照片组供用户补充正确标签，但标记推流依据失效并禁用
  `P` / `X`；用户完成修正后显式舍弃该组，不产生负样本。
- 接受、明确拒绝、忽略、稍后处理都保留在底部直接可见；明确拒绝按钮显示选中数量与标签名，不放进
  “更多”菜单。

### CT-P6：右侧检查器优先编辑所选照片标签，并保留可折叠的推流范围

- 进入智能推流时默认展开右侧检查器，上半部分复用图库标签面板的分组、折叠、流式标签布局、混合状态、
  左键确认和右键清除；下半部分以 DisclosureGroup 保留推流范围，避免照片标签与范围选择混用同一动作。
- 顶部只保留当前范围摘要，点击摘要可重新展开检查器，不再用会反复关闭的超长菜单承载标签选择。
- 默认“智能推荐”不排除任何 active 标签，但把地点/场景、活动/事件等
  依赖时间、位置和拍摄事件才能表达的标签组排在前面；人物、美食、动植物、文档等可由图像内容分类的
  标签组排在后面。
- 系统组以稳定 group ID 判断；用户创建的组以组名分类。排序只使用用户拥有的标签分组语义，不根据某张
  照片内容猜测标签含义，也不硬编码“旅游”“板栗”等具体标签白名单。
- 同一语义层内，无已激活图片模型的标签优先于已有 Feature Print 或个人图片模型的标签；随后依次按
  accepted 人工决定较少、当前组候选较多、创建时间较早排序。已有模型或大量样本只降序，不删除候选。
- 用户可切换到“自选标签范围”并勾选一个或多个标签；生成、待确认计数和当前组读取都只针对该集合。
  选择保存在本机偏好中；标签归档或删除后从集合移除，集合为空时自动回到“智能推荐”。

### CT-P7：推流网格复用图库与瘦身工作台的缩略图展示契约

- 智能推流工具栏直接复用图库瘦身的九档缩略图大小菜单，以及“正方形 / 原比例”切换；同一个
  `LibraryWorkspaceModel` 中的图库、审核、瘦身和推流共享当前展示设置。
- 推流网格使用 `LibraryGridLayout` 的固定列宽、间距和滚动条预留宽度，不再维护独立的固定 170–240 点卡片。
  改变大小或比例只能重排当前照片组，不得刷新候选、清除锚点/候选选择或改变提交集合。
- “原比例”继续遵守 ADR-047：只查询已手动生成的 `gridOriginal` 缓存；缓存缺失、损坏或读取失败时回退
  正方形网格缩略图。切换查看方式不得读取原始媒体、请求 iCloud 或隐式创建新缓存。

## 取舍

- 独立表比复用 `prediction` / `personal_prediction` 多一个持久化概念，但能明确区分上下文、模型和人工事实，
  并支持组级忽略、证据解释与恢复。
- Photos 资产只使用现有时间与位置，不伪造目录；文件夹资产可额外使用文件序列。缺失证据会降低召回，
  但不会扩大真实照片访问边界。
- 组级 UI 比逐行塞入 Review Queue 多一条产品路径，但能完整表达锚点、连续段、逐张排除和组级忽略。
- 完整桌面选择比逐张复选增加了范围锚点、框选命中和键盘监控状态，但能避免大量候选时反复点击；统一的
  candidate 归一化边界保证锚点和陈旧成员不会进入标签事务。
- 共享缩略图展示设置意味着用户从图库或瘦身切入推流时会沿用当前九档大小与比例，而不是为每个页面记忆
  一套独立值；这样减少设置分裂，也保持现有原比例缓存安全边界。
- 智能推荐采用标签组语义而非逐标签硬编码，可能无法准确理解命名模糊的自定义组；自选范围为用户保留
  明确控制，且不会改变或删除已经生成的候选组。
- 先独立规则、后模型融合会多一个阶段，但可以在零模型样本时立即提供价值，并能单独测量规则质量。

## 被否决的方案

1. **自动把同目录连续文件全部标记为同一标签**：错误会直接污染人工事实与训练样本，否决。
2. **把文件名候选伪装成 `personalModel` prediction**：丢失证据来源和组级状态，否决。
3. **把“忽略组”写成 rejected**：忽略只否定当前启发式，不否定照片标签，否决。
4. **首版同时做上下文与 embedding 融合**：无法独立评估规则质量，且延迟首个闭环；模型延期到 V2。
5. **浏览器端自行生成组**：会造成 Mac/Web 规则漂移且需要暴露更多路径信息，否决。
6. **同目录、同地点或同设备即可成组**：这些弱信号跨度可能达到数月，必须由短时间、近距离或文件序列等
   额外证据支持，否决。

## 后果

- 已实施 `v038_add_contextual_tag_feed`，包含 feed、member 和 evidence，未改写 v001-v037；唯一组身份为
  `tag_id + source_id + group_key + policy_revision`。设备 schema 与回填在后续 migration 单独交付。
- `ContextualTagFeedService` 通过现有标签仓库的事务内批量决定能力，把人工决定与 feed 状态变更原子提交。
- 同一标签、来源和策略的重叠 pending 组复用最早组；候选已在其他入口被决定时，陈旧组自动结束，提交前
  仍会在事务内再次验证，避免覆盖更新的人工事实。
- Review Queue 的刷新连续性契约继续有效：处理 feed 后只局部移除/推进当前组，不重载用户已浏览窗口。
- 首版产品选择已确认：侧栏独立入口、候选默认全选、组上限 24、完整桌面多选/全选，并将明确负标签作为
  右下直接可见动作。
- 推流顶部提供持久化标签范围；默认按上下文依赖程度与模型成熟度排序，自选范围则只生成、统计和显示
  被选标签，不修改其他 pending 组。
