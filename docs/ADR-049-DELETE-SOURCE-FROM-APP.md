# ADR-049：删除来源即删除其 ImageAll 目录事实

- 状态：已决定（2026-08-02；2026-08-03 补充回收生命周期）
- 范围：macOS ImageAll 来源管理；文件夹来源与 Apple Photos 来源

## 背景

旧界面的破坏性操作实际是“停用来源”：只把 `source.state` 改为 `disabled`，继续保留
Source、Asset、人工标签关系和缓存。用户把该操作理解为删除后，侧栏仍显示“已停用”来源，
图库仍显示无法读取的照片占位，这与“删除来源后从 App 消失”的产品语义冲突。

## 决策

来源菜单不再把“停用来源”作为面向用户的删除动作，改为“删除来源…”。用户确认后：

1. 先停止该来源的 watcher、缩略图预热和新扫描，并取消/收敛相关任务；
2. 删除该来源照片的 ImageAll 自有预览与 Photos 原图缓存；
3. 在单个数据库事务中删除直接关联的回收历史、人工标签决定、来源任务、Asset 和 Source；
4. 清除当前来源选择、照片选择、Inspector 和侧栏排序残留，成功后回到“全部照片”；
5. 标签定义属于全局用户资料，不因删除单一来源而删除；失去照片引用的标签仍可用于其他来源；
6. 磁盘原文件与 Apple Photos 资产始终不修改、不移动、不删除。

删除来源预检把未解决项目分成三类，并向界面返回各自数量：

1. `recycled` 是真实回收项目。文件夹媒体必须由用户选择恢复，或在独立的破坏性确认后永久
   清理；Apple Photos 媒体仍按系统“最近删除”恢复。删除来源绝不隐式永久清理这些项目；
2. `file + failed + mutationAuthorizationRequired` 是可撤销的“文件操作前失败意图”。
   `FolderMutationAccessService` 在解析/进入写权限闭包前抛出此错误，
   `FolderQuarantineIO` 尚未被调用。用户可在回收站执行“撤销失败记录”；该动作只删除这条失败
   意图，不访问、写入、移动或删除原位置与隔离区文件。若用户后来重试成功，同一 Asset 的更新
   `recycled` 记录继续独立保留，并仍要求恢复或永久清理；
3. 其他 `pending` / `restoring` / `purging` / `failed` 均属于位置或持久化状态未确定。它们继续
   阻止来源删除，显示错误原因，并提供重新检查或处理说明，不会被自动忽略。文件型失败重新检查
   时，只有原位置存在会收敛为 `restored`，只有隔离区存在会收敛为 `recycled`；两边都存在或都
   不存在仍保持阻塞，且不会删除任一侧文件。

不能把规则简单放宽为“所有 `failed` 均不阻止”。移动可能已完成但数据库提交失败，或者原位置
与隔离区同时存在/同时缺失；丢弃这类记录可能直接丢失唯一恢复入口，或把不确定的媒体误报为安全。

删除被阻止时，主界面立即显示操作对话框，并在底部保留可回看的状态提示；两处都明确说明
“删除没有在后台继续”、显示上述分类数量并提供“前往回收站”。该入口把回收站限定到当前来源，
避免阻塞项目被全局列表淹没。回收站列表展示所有未解决状态，不再只展示 `recycled`。

历史 `disabled` 文件夹仍允许在用户明确触发恢复时解析其独立写授权；新的回收/快速删除记录插入
继续要求 Source 为 `active`，因此该兼容能力不能在已停用来源上启动新的照片变更。若权限已失效，
用户可重新选择同一来源更新回收权限后再恢复。

## 原子性与失败语义

- 来源删除与交互式回收共享同一个排他变更窗口；先执行一次无副作用预检，再停用来源以禁止新的
  回收意图，然后执行第二次预检。因此回收阻塞会在停用来源前拒绝，Source/Asset/缓存保持不变；
  第二次预检用于防御不经过当前进程闸门的数据库并发写入；
- 第二次预检通过后才清理可重建缓存；任一缓存清理失败时不删除 Source/Asset，允许重试；
- 数据库删除在一个事务中执行，任何约束或并发变化都会整体回滚；
- 成功标准是来源查询不到、其 Asset 和直接关联事实查询不到、相关任务不再出现在活动记录；
- 删除操作不会取得或使用来源写权限，因此不构成真实照片删除授权。

## 兼容性

数据库继续识别历史 `disabled` 状态，使旧目录可在新版本中直接执行“删除来源…”，也可先解决
遗留回收项目。底层停用能力暂时保留给兼容与任务收敛使用，但不再作为用户期望的删除结果。
