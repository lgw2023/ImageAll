# USB migration cold-recovery memory regression

This executable invokes the production transfer store and archive verifier in a
fresh process, without the App, Photos, real user media, network, or LLDB. The
Python runner creates only a new synthetic directory, using sparse zero files.
All bytes are still read and hashed; elapsed time is **not** an HDD/USB benchmark.
The parent samples both resident memory and physical footprint every 10 ms,
kills the child above 512 MiB or 180 seconds, and fails closed if sampling fails.
Build separately with `--jobs 2`; do not run alongside other large builds/tests.

```sh
swift build --package-path scripts/usb-memory-regression --scratch-path /tmp/ImageAllMemoryBuild --jobs 2
python3 scripts/usb-memory-regression/run.py /tmp/ImageAllMemoryBuild/debug/RecoveryProbe /tmp/ImageAllSynthetic2889 /tmp/ImageAllMemoryEvidence/batch.json --create 2889 --archive
python3 scripts/usb-memory-regression/run.py /tmp/ImageAllMemoryBuild/debug/RecoveryProbe /tmp/ImageAllSynthetic2889 /tmp/ImageAllMemoryEvidence/second-process.json
python3 scripts/usb-memory-regression/run.py /tmp/ImageAllMemoryBuild/debug/RecoveryProbe /tmp/ImageAllSynthetic4GiB /tmp/ImageAllMemoryEvidence/large.json --create 1 --chunks-per-file 1024 --archive
```

`--archive` exercises a journaled manifest plus 2,889 resources, discards a
synthetic uncommitted tail, checks durable resource receipts, replays a committed
chunk without increasing offsets, seals twice, and visits all verified records.
The repeated invocation starts a new process over the already sealed journal.
The large-file case proves buffers are released within a file, not just between
files. Swift package regressions separately prove byte-offset resume and rejection
of changed data (including cold recovery with a prior verified receipt).
JSON reports contain peak physical footprint, peak RSS, duration, stop reason and
all samples. An adjacent log contains phase outcomes. Exit 0 requires all assertions.

For a separately authorized real-App acceptance run, `watch_app.py` waits for
one exact Xcode executable path and monitors only that PID. It never launches or
restarts the App. Its default 1 GiB guard sends TERM then, if still alive after
2 seconds, KILL; the durable transfer journal recovers any uncommitted tail.
Confirm the report says `waiting-for-exact-app` before launching, then `watching`.
A stopped guard must be investigated, never treated as permission to auto-retry.
The configurable lower threshold exists for synthetic guard self-tests only.

## Client-to-store resume scenario

`ResumeScenarioProbe` adds the production `RemoteLibraryClient` and transfer
store to a synthetic in-process HTTP adapter. `prepare_resume.py` creates a new
receiver journal containing 2,888 verified small resources and a 4 GiB resource
with all but 8 MiB committed, plus an uncommitted tail. The first process checks
the cold journal, uploads only the suffix, and verifies/seals 2,889 resources.
A second independent process must reuse the migration and upload zero resource
and metadata bytes. Each process writes its own timing/counter result.

```sh
swift build --package-path scripts/usb-memory-regression --scratch-path /tmp/ImageAllResumeBuild --jobs 2
python3 scripts/usb-memory-regression/prepare_resume.py /tmp/ImageAllResumeSynthetic
python3 scripts/usb-memory-regression/run.py /tmp/ImageAllResumeBuild/debug/ResumeScenarioProbe /tmp/ImageAllResumeSynthetic /tmp/ImageAllResumeEvidence/first.json
python3 scripts/usb-memory-regression/run.py /tmp/ImageAllResumeBuild/debug/ResumeScenarioProbe /tmp/ImageAllResumeSynthetic /tmp/ImageAllResumeEvidence/repeat.json
```

Use fresh task-owned paths. All runs retain the 512 MiB guard; investigate a
failure before rerunning. `firstEffectiveProgressSeconds` means the time until
the authenticated, validated receiver checkpoint can support skipping resources;
it is not first app paint, first uploaded byte, or final completion. The separate
`fiveSecondTargetMet` field reports the performance target without concealing
successful integrity checks when that target is missed.

The prepared journal models existing durable state. This probe excludes the
iOS UI, PhotoKit preparation, USB/TLS, Mac catalog publication and task-intent
loading (tested separately by `scripts/mobile/ShareTaskRecoveryTests.swift`).
The source uses generated bytes and sparse zero ranges, so this is a recovery
and memory regression, not a USB/disk throughput benchmark or media-decoder test.

## Same-task HTTP and catalog integration

`scripts/mobile/run_import_task_e2e.py` compiles the current mobile task/journal
and client into a direct XCTest bundle with the Mac HTTP tests. Supply the current
macOS Debug products and their successful build log; the runner extracts module
search paths and records source/binary fingerprints. It never launches the App
test host. Use a new task-owned output directory outside protected HDD2.

```sh
python3 scripts/mobile/run_import_task_e2e.py \
  --products /absolute/path/to/DerivedData/Build/Products/Debug \
  --build-log /absolute/path/to/mac-build.log \
  --output /absolute/path/to/new-synthetic-evidence
```

One generated 8 MiB resource is interrupted after a real 4 MiB HTTP ACK. Reloading
the task and receiver preserves the task/batch and explicit pause; manual resume
sends only the remaining 4 MiB. The same task observes waiting, verification,
publication and browsable states through authenticated HTTP and a real isolated
catalog. Repeated recovery sends no resource or metadata bytes. Same-size damage
in a second generated batch must report `resourceChanged`, surface
`needsAttention`, and leave the publication count unchanged.

`result.json` is the 512 MiB guarded XCTest result; `scenario-result.json` contains
stage and byte evidence. The latter alone is not a pass verdict. Phase boundaries
are driven by a synthetic coordinator using the same operations as the Mac UI;
USB/TLS, PhotoKit, the UI controller and iOS lifecycle are excluded. This is not
a real-phone throughput or cold-start timing result.

## Physical USB task acceptance

The same runner accepts `--device-config /absolute/task/Evidence` and selects
`USBImportDeviceHostTests.swift`. This is an interactive device fixture, with a
30 minute timeout and the same independent 512 MiB Mac process guard. It requires
an explicit `run-config.json` (runID, hostID, port, certificate fingerprint), a
task-owned `synthetic.p12` with password `synthetic-only`, and an independent iOS
build using `USB_IMPORT_ACCEPTANCE`. Never use a production certificate.

Build the phone project with bundle ID `com.gwlee.ImageAllMobile.USBAcceptance`,
an independent Info.plist and explicit task-owned `SYMROOT` and `OBJROOT` (global
Xcode location settings can override `-derivedDataPath`). Launch with
`--usb-import-task-probe RUN_UUID HOST_UUID CERTIFICATE_SHA256`. This entry point
fails closed for other bundle IDs or missing arguments; it does not construct
the Photos model. Its data, preferences and Keychain service are independent.

After the phone is active and listening, write a unique `connect-N` to the host
output's `command.txt`. Start via the phone button. At the 4 MiB ACK gate, unplug
the physical cable for at least five seconds, then reconnect and explicitly
continue the same task. At the 12 MiB gate, send the App to the background and
return, reconnect and explicitly continue. Once received, write `publish` to
observe real verification/publication through authenticated status polling, then
`finish` to close the guarded test. The host requires physical USB disappearance
and a published isolated source. Independently inspect phone reports for task ID,
pause causes, offsets, bytes and the final visible result; host success alone is
not full device acceptance. Five-second phase dwell windows are for observation,
not performance measurements. Phone memory is self-sampled, not an independent
OS peak measurement. Preserve original phone journal and read-only Mac catalog
summaries before and after; original batches must not participate.
